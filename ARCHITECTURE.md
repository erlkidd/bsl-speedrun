# bsl-speedrun.kz — архитектура и стек

## Ключевая идея
Статический фронт со всем контентом (задачи, тесты, база знаний) + маленький бэкенд, который
запускает OneScript в одноразовом Docker-контейнере без сети и файлов + BSL Language Server для линтера.
Всё в одном docker compose на VPS, HTTPS на домене автоматически через Caddy.

## Стек
| Слой | Что | Почему |
|---|---|---|
| Фронт | **Vite + React** (SPA) | меньше движущихся частей; контент из `content/` подтягивается при сборке |
| Редактор | **Monaco** + подсветка BSL (Monarch-грамматика) | тот же движок, что в VS Code |
| Линтер | **BSL Language Server** в режиме `websocket` + свой лёгкий LSP-клиент (`web/src/lib/lsp.js`) | живые диагностики, автодополнение, hover — как в VS Code |
| Синтаксис | `oscript -check` на бэке + ошибки парсера BSL LS в редакторе | двойная проверка |
| Выполнение | **OneScript 2.x** в Docker | настоящий движок BSL без платформы |
| API | **Node.js + Fastify** | общий язык с фронтом, просто спаунить контейнеры |
| Запросы | свой движок языка запросов 1С на JS (`web/src/lib/q1c`) над виртуальной конфигурацией | выполняется в браузере: мгновенно, без нагрузки на сервер и без платформы |
| Прогресс | профиль (имя + пароль) → JSON-файл в томе `apidata`; гость — localStorage | без внешней БД; при росте заменить на SQLite |
| 3D-помощник | three.js, модель из примитивов, отдельный lazy-чанк | не тянет файлы моделей и не тормозит первую загрузку |
| Хостинг | VPS 2 vCPU / 4 ГБ, Ubuntu, **Docker Compose + Caddy** | Caddy сам получает Let's Encrypt для домена |

## Схема
```
Браузер ──HTTPS──> Caddy ─┬─ /            → статика (Vite build)
                          ├─ /api/run     → api (Fastify, unix-сокет, без сети) → oscript
                          ├─ /api/check   → api → oscript + тест-харнесс задачи
                          └─ /lsp (wss)   → bsl-language-server (websocket)
```

## Песочница OneScript (безопасность)
Главная защита — контейнер `api` целиком без сети (`network_mode: none`), с read-only FS, `cap_drop: ALL`,
лимитами памяти/CPU/процессов; Caddy достучится до него только через unix-сокет в общем томе.
Docker-in-Docker и доступ к docker.sock не нужны. Каждый запуск — отдельный процесс `oscript` во временном каталоге,
таймаут 5 с, вывод до 64 КБ.
Дополнительно (defense in depth) — статический запрет до запуска: `КомандаСистемы`, `ЗапуститьПриложение`,
`Новый Файл/ЧтениеТекста/ЗаписьТекста/HTTPСоединение/COMОбъект`, `ПодключитьСценарий`, `ЗагрузитьСценарий`,
`#Использовать`, `Выполнить`/`Вычислить`. Очередь + лимит запросов по IP (rate limit) в API.
`Сообщить()` → stdout → показываем в консоли на странице.

## BSL Language Server (полная поддержка)
Отдельный контейнер `bsl-ls` (Java 17+, `java -Xmx768m -jar bsl-language-server.jar websocket --server.port=8025`),
Caddy проксирует `wss://bsl-speedrun.kz/lsp`. В Monaco через свой LSP-клиент (`web/src/lib/lsp.js`, без тяжёлых зависимостей) получаем:
- **диагностики** (синтаксис + ~150 правил стандартов 1С) — подчёркивания и панель «Проблемы»;
- **автодополнение**, **hover** с описанием методов, **сигнатуры**, **переход к определению**, **outline**;
- **форматирование** кода (кнопка «Форматировать»);
- **quick fix** там, где BSL LS их даёт.

*План:* общий конфиг `.bsl-language-server.json` (отключить правила, бесполезные для учебных фрагментов) и
«строгий режим» задач — диагностики BSL LS из `meta.yaml` считаются ошибкой. Без BSL LS сайт работает:
остаётся `oscript -check`.

## Практика: формат задачи
Каждая задача — папка в `content/tasks` (формат — в README):
```
tasks/011-sum-array/
  task.md          # условие (Markdown)
  meta.yaml        # сложность, теги, подсказки[], запреты/требования
  starter.os       # заготовка: Функция СуммаМассива(Массив) Экспорт ... КонецФункции
  solution.os      # эталон (показывается по кнопке)
```
Тесты описываются в `meta.yaml` (args/expected), API сам генерирует проверочный BSL-код.
Проверка «по-своему» = 3 уровня:
1. **Синтаксис** — `oscript -check`.
2. **Правила задачи** (meta.yaml): обязательные/запрещённые конструкции (напр. «использовать `Для Каждого`»,
   «без `Запрос` в цикле»). *План:* выбранные диагностики BSL LS тоже считать ошибкой.
3. **Тесты** — код ученика + `api/runtime/harness.os` + сгенерированные вызовы в одном запуске;
   харнесс печатает строки `##CASE##`, фронт показывает таблицу кейсов.

## Теория (квиз)
`content/quiz/*.yaml`: вопрос, варианты, правильный, объяснение для каждого неверного.
Неверный ответ → подсвечиваем правильный + показываем объяснение + ссылку на статью БЗ. Всё на клиенте, без бэка.

## База знаний
`content/kb/general/*.md` и `content/kb/bsp/*.md` — Markdown с frontmatter, поиск по статьям на клиенте, подсветка BSL.

## Хостинг на домене
1. VPS (ps.kz / Hoster.kz — ближе к КЗ, или Hetzner), Ubuntu 24.04, ставим Docker.
2. У регистратора домена: A-запись `bsl-speedrun.kz` (и `www`) → IP VPS.
3. `git clone` + `docker compose up -d` — Caddy сам выпустит сертификат.
4. Деплой обновлений: GitHub Actions → ssh → `git pull && docker compose up -d --build`.

## Этапы
1. **Песочница**: Monaco + `/api/run` + Docker-раннер. (ядро, всё остальное на нём)
2. **Линтер**: BSL LS websocket в Monaco.
3. **Практика**: формат задач, харнесс, 10–15 первых задач.
4. **Теория-квиз** + **БЗ** (контент можно писать параллельно).
5. Аккаунты и прогресс, рейтинг/«спидран»-таймер.

## Риски, проверить прототипом
- Как BSL LS websocket держит несколько клиентов одновременно (при проблеме — пул процессов или линт по запросу
  через постоянно запущенный BSL LS).
- Память: BSL LS (Java) ~0.5–1 ГБ → VPS не меньше 4 ГБ.
- Холодный старт `docker run` ~0.3–0.7 с — для MVP нормально, позже пул «тёплых» контейнеров.
